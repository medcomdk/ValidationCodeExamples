## A. Загальний діагноз

### Виявлена архітектура
ValidationCodeExamples містить приклади валідації клінічної FHIR на .NET (Firely SDK), розроблений MedCom (medcomdk). Це проєкт .NET 10 (net10.0) з одним проєктом демонстрації `FirelySDKDemo`, який:
- Завантажує пакети FHIR (IG MedCom CareCommunication 5.0.1) через `FhirPackageSource`
- Створює кешований resolvedor ресурсів (`CachedResolverUtilities`)
- Створює сервіс термінології (локальний + MIME + зовнішній `https://tx.hl7europe.eu/r4`)
- Створює валідатор FHIR (`Validator`)
- Десеріалізує повідомлення Care Communication (XML/JSON) та валідує
- Виводить помилки/попередження валідації

Файли:
- `FirelySDKDemo/FirelySDKDemo.sln`, `FirelySDKDemo.csproj` (net10.0)
- `Program.cs` — точка входу (запускає CareCommunicationDemo)

- `AckDemo.cs` — демо підтвердження (закоментовано в Program.cs)

- `Resources/CareCommunication/*.xml, *.json` — приклади повідомлень

## B. Виявлені проблеми

| ID | Назва | Severity | Статус | Локація |
|----|-------|----------|--------|---------|
| REA-015 | InvalidOperationException через `Coding.First()` коли список порожній | P2 | ПІДТВЕРДЖЕНО | `FirelySDKDemo/Program.cs:84` |

### Деталі

**REA-015 — `Coding.First()` може кинути InvalidOperationException (ПІДТВЕРДЖЕНО)**
- Проблема: `Program.cs:84` викликає `issue.Details?.Coding.First().CodeElement?.Value`. Якщо список `Coding` порожній, `.First()` кидає `InvalidOperationException` (немає елемента).
- Довід: `Program.cs:84` — `Console.WriteLine($"IssueCode: {issue} - Issue details {issue.Details?.Text} - Error Code : {issue.Details?.Coding.First().CodeElement?.Value}");`
- Причина: використання `.First()` на колекції, яка може бути порожньою, без перевірки.
- Наслідок: виведення проблем валідації може вийти з винятком, коли проблема не має кодів Coding.
- Пропонована виправка: замінити `.First()` на `.FirstOrDefault()` з перевіркою null.

## C. Повторювані проблеми

Повторювана проблема, вже задокументована підтримувальниками і у процесі виправлення:
- `conformsTo()` не підтримується в .NET FhirPath engine → 3 попередження BusinessRule (medcom-messaging-1, medcom-careCommunication-1, medcom-careCommunication-3).
- Джерело: `README.md` (рядки 17-19 і 21: "We are currently developing a new patch of our IGs to resolve the BusinessRule issue types of conformsTo").
- Статус: вже визнано支持никами; не є дефектом для виправлення в цьому аудиті.

Проблема, попередньо виправлена支持никами (доведення в історії):
- Коміт `22822a7` "Don't throw exception when trying to patch ecpr" — змінив `CachedResolverUtilities.cs`, використовуючи `continue` з попередженням, коли canonical не знайдено, замість винятку.
